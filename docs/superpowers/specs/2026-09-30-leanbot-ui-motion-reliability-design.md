# Leanbot UI And Motion Reliability Design

## Outcome

Improve the imported LeanbotSerial IDE without changing its overall structure or
the public shape of the eight My Blocks. A successful Compile returns the user to
the full editor, Upload gives an explicit success or failure message, stale static
assets no longer cause blank or malformed layouts, and generated My Blocks code
moves more responsively while keeping the documented Leanbot speed limit and
improving motion accuracy.

The **My Blocks** toolbox category and every block in that category use the same
blue `#3373CC` already used by the Leanbot Motion category. Existing serialized
Blockly projects remain compatible because block type names and field/input names
do not change.

## Scope

This change covers two connected areas, implemented through independent gates so a
UI regression cannot be hidden by motion work and motion work cannot be declared
complete from browser tests:

1. The existing Compile/Upload feedback and editor-panel lifecycle in the imported
   IDE.
2. The C++ runtime generated by the eight existing My Blocks.

- **Gate A — IDE lifecycle and appearance:** Compile/Upload feedback, asset
  versioning, and the blue My Blocks theme. Gate A must pass its browser checks
  before Gate B starts.
- **Gate B — generated motion runtime:** input validation, motion/FLL controllers,
  generator checks, and remote sketch compilation.
- **Gate C — physical calibration:** repeatable robot measurements. Gate C may tune
  centralized constants but may not change block signatures or UI behaviour.

It does not replace the Leanbot library, bypass its motor scheduler, or drive the
stepper pins directly. `LbMotion.runLR()` remains the only wheel-command boundary.
Its documented range is `-2000..2000` steps per second, so the public Speed scale
continues to map linearly from `0..100` to `0..2000`. Move alone accepts negative
Speed for reverse motion.

## UI Behaviour

### Compile

- Clicking Compile opens the PROGRAM panel and shows progress as it does today.
- `LeanbotCompiler.onCompileSucess` is the sole Compile-success signal. After its
  log assignment and toast call finish, `uiHideSerialTab()` runs immediately and
  restores the full editor height. No timer or delayed callback is used.
- A successful log containing `/\bwarning:/i` receives the toast text
  `Compile Successful With Warnings`; other successful logs receive
  `Compile Successful`. Both close PROGRAM, and both logs remain available by
  reopening SERIAL/PROGRAM.
- On a compile error, the PROGRAM panel remains open, the progress state is marked
  as failed, and the existing compiler log remains visible.
- The Compile click handler wraps the awaited compiler call in `try/finally`.
  Compile controls, Connect, and the file tree are re-enabled in `finally`, so a
  rejected request cannot leave the IDE looking frozen or blank.

### Upload

- Upload success means `compileAndUpload2()` returns `{success: true}` only after
  `#uploadCode()` has completed both page writes and `#verifyUploadedCode()` without
  throwing. Only that state displays: `Upload Successful — You Can Disconnect The
  USB Cable And Run The Robot.`
- After success the existing transition to the serial monitor remains intact.
- `exception === "cancelled"` invokes the existing cancellation UI and does not
  show `Upload Error`. Every other false result shows `Upload Error`; connection
  exceptions keep their existing detailed modal. Compile, transfer, write, and
  verify failures retain the detailed PROGRAM log.
- `runCompileUploadFlow2()` uses `try/finally` around the complete call plus
  `uploadFlush()`. It resets `isCompileAndUpload` and restores Compile, Upload,
  Connect, and tree controls for success, cancellation, thrown errors, and false
  results.

### Static Assets And Layout

- Use the literal release token `20260930-2` on every locally modified entry asset:
  outer `styles.css`, outer `main.js`, `LB-blockly/index.html`, inner
  `themes_categories.js`, inner block definition `myblocks.js`, and inner Arduino
  generator `addon/myblocks.js`. The token is bumped whenever one of those files is
  deployed. This guarantees fresh modified assets once the current HTML document
  has been fetched; it does not claim to override an intermediary that serves stale
  HTML against HTTP cache rules.
- The current flex/grid layout stays unchanged. The fix removes the cache mismatch
  that can create blank or malformed regions rather than redesigning the IDE.

## My Blocks Appearance

- Change `myblocks_category.colour` from pink to `#3373CC` in the Blockly theme.
- The toolbox category and all eight blocks already reference
  `myblocks_category`, so one theme-token change updates both consistently.
- Do not add per-block colours or duplicate CSS overrides.

## Generated Motion Runtime

### Shared Rules And Interfaces

- Inputs are rejected rather than silently clamped. Move accepts finite Speed in
  `[-100,-1] U [1,100]`; Turn and FLL accept finite Speed in `[1,100]`. A dynamic
  negative Turn/FLL value is invalid just like a negative literal. Distance accepts
  `[0.1,1000]` cm, Angle `[1,3600]` degrees, and Time `[0.1,600]` seconds.
- Valid speed mapping is linear. Magnitude is
  `targetSpeed = round(abs(speedPercent) * 20)`, producing `20..2000`. Move applies
  the original sign after mapping; Turn direction comes only from the Left/Right
  block; FLL is forward-only.
- Every context is value-initialized (`ctx = {}`) before use. This removes the AVR
  uninitialized-field warnings and makes initialization safe if control flow later
  changes.
- Invalid numbers, zero speed, out-of-range target values, a lost line, or a stall
  always stop through `LbMotion.stopAndWait()` and return.
- `LbmbState` contains `uint32_t timeMs`, `int32_t distanceMm`,
  `int32_t rotationDeg`, and `uint8_t lineState`. `LbmbCommand` contains
  `int16_t leftSpeed`, `int16_t rightSpeed`, and `bool isDone`.
- The Arduino-independent functions remain
  `lbmbMoveCoreStep(LbmbMotionCtx*, const LbmbState*, float, float)`,
  `lbmbTurnCoreStep(LbmbMotionCtx*, const LbmbState*, float, float, bool)`, and
  `lbmbFollowCoreStep(LbmbFollowCtx*, const LbmbState*, float, uint8_t, float)`.
  Wrappers alone call `millis()`, Leanbot sensors/odometry,
  `LbMotion.runLR()`, and `LbMotion.stopAndWait()`.

Initial centralized constants are deterministic and provisional until Gate C:

| Constant | Initial value |
|---|---:|
| Control tick | 10 ms |
| Minimum moving speed | 200 steps/s |
| Acceleration increment | 40 steps/s per tick |
| Deceleration increment | 80 steps/s per tick |
| Move brake distance | `clamp(targetSpeed / 25, 15, 80)` mm |
| Heading `Kp`, `Kd`, correction limit | `16`, `28`, `currentSpeed / 4` |
| Turn coarse lead | `clamp(targetSpeed / 100, 5, 20)` degrees |
| Turn fine speed | `min(targetSpeed, 250)` steps/s |
| Turn tolerance / fine passes | 2 degrees / at most 2 passes |
| FLL `Kp`, `Ki`, filtered `Kd` | `220`, `2`, `60` |
| FLL integral limit | `[-30,30]` |
| FLL derivative filter | `(3 * previous + rawDelta) / 4` |

### Move With Speed And Distance

- Initialize `currentSpeed` to `min(targetSpeed, 200)`. Each 10 ms tick raises it by
  at most 40. Speed 50 therefore reaches 1000 steps/s in at most 200 ms instead of
  the current roughly 670 ms.
- Let `remainingMm = targetMm - progressMm` and `brakeMm` be the table value. Outside
  the brake region the desired speed is `targetSpeed`. Inside it, desired speed is
  `200 + (targetSpeed - 200) * remainingMm / brakeMm`, bounded to
  `[min(targetSpeed,200), targetSpeed]`. `currentSpeed` falls by at most 80 per tick.
- Heading error is `rotationDeg - startRotationDeg`; derivative is the current error
  minus the previous error. Correction is `16*error + 28*derivative`, clamped to
  `[-currentSpeed/4,currentSpeed/4]`. For forward or reverse, signed base speed is
  combined as `left = base - correction`, `right = base + correction`, then both
  outputs are clamped to `[-2000,2000]` without changing the requested travel sign.

### Turn Left/Right

- Continue measuring signed body rotation with `LbMotion.getRotationDeg()`; the
  documented Leanbot convention is positive for Right and negative for Left.
- The coarse pass starts at `min(targetSpeed, 200)` and applies the same 40
  steps/s-per-10-ms acceleration increment as Move until either the requested
  target speed or its angle-braking envelope is reached. The envelope linearly
  approaches 200 steps/s across the final `max(coarseLead, 5)` degrees, with the
  same 80 steps/s-per-tick deceleration limit.
- The first pass uses the normal target speed but intentionally stops at
  `max(0, targetAngle - coarseLead)`, where `coarseLead` is the table value. It then
  calls `stopAndWait()` before measuring the settled angle. This directly addresses
  the current defect where stopping begins only after 90 degrees is reached.
- Settled error is `requestedSignedAngle - measuredSignedAngle`. If its magnitude is
  greater than 2 degrees, a fine pass turns in the error's direction at at most 250
  steps/s. Stop one degree before the remaining target, settle, and measure again.
  Perform at most two fine passes; then stop even if error remains, preventing an
  oscillating robot on a slippery surface.
- Left and Right use the same equations but keep separate centralized coarse-lead
  constants so Gate C may tune asymmetric hardware without changing the blocks.

### FLL Controllers

- Use only the pinned and already compiling `LbIRLine.read()` contract. The error
  table remains `1000:-3`, `1100:-2`, `0100/1110:-1`, `0110/1111:0`,
  `0010/0111:+1`, `0011:+2`, and `0001:+3`. This avoids introducing an unverified
  analog-channel order or calibration dependency.
- Analog centroid assistance is intentionally out of scope: it was not part of the
  requested block contract, and this imported Leanbot build does not pin a tested
  sensor-index, polarity, or calibration contract for `LbIRArray`. It may be added
  later only with a library-version-specific hardware test, without changing these
  blocks.
- Integral candidate is clamped to `[-30,30]`. Raw derivative is
  `error - previousError`; filtered derivative uses the table equation. Correction
  is `220*error + 2*integral + 60*filteredDerivative`.
- The requested base speed is the outer-wheel ceiling rather than allowing PID to
  boost a wheel above the user's Speed. For negative error the left wheel is the
  inner wheel; for positive error the right wheel is inner. The inner command is
  `baseSpeed - abs(correction)`, clamped to `[0,baseSpeed]`. State magnitude 3 is a
  deliberate sharp-recovery case and sets the inner wheel to zero.
- Do not integrate while the inner output is saturated and the new integral would
  increase saturation. This is the anti-windup rule.
- Base speed uses the same 40-up/80-down slew. The distance variant applies the
  Move braking equation to remaining millimetres. The time variant uses
  `brakeMs = clamp(targetSpeed / 2, 200, 800)` and linearly approaches 200 steps/s
  over the final `brakeMs`, again bounded by the 80-per-tick deceleration limit.
  Marker variants require three consecutive matching samples before stopping.
- Calibration remains the responsibility of the existing Leanbot calibration API;
  this change does not insert an interactive calibration sequence into every My
  Block call.

## Boundaries And Data Flow

```text
Blockly values
  -> generator validation and C++ helper emission
  -> Arduino wrapper reads time, odometry, and digital line state
  -> pure motion/FLL core calculates bounded left/right commands
  -> LbMotion.runLR()
  -> stop condition calls LbMotion.stopAndWait()
```

The UI flow remains separate:

```text
Compile/Upload click
  -> lock controls and open PROGRAM
  -> compiler/uploader callbacks update progress and log
  -> success toast + requested panel transition
     OR failure toast + keep PROGRAM open
  -> finally restore controls
```

## Error Handling And Safety

- Never generate wheel commands outside `-2000..2000`.
- Never attempt a direct-stepper workaround to exceed the Leanbot API limit.
- Preserve stall and lost-line timeouts so a blocked or derailed robot stops.
- Preserve marker and overall-operation timeouts.
- Clamp heading and line corrections before combining them with base speed.
- Do not claim physical PID completion from software tests alone. Final constants
  require repeatable runs on the actual robot and track.

## Verification

### Automated

- Static/generator tests confirm all eight blocks retain their public types and emit
  the expected helper calls.
- Theme tests confirm `myblocks_category` is blue and all My Blocks reference it.
- A generator harness executes the actual Blockly generator and captures the exact
  C++ string stored in `definitions_['myblocks_runtime']`; assertions target that
  emitted source rather than a separately hand-written C++ copy.
- A host C++ harness compiles and executes the exact captured runtime string with
  mocked `millis`, odometry, line state, and `LbMotion` calls. It covers input
  rejection, linear speed mapping, the 200 ms Speed-50 ramp, command bounds,
  forward/reverse heading correction, coarse/fine turn braking with simulated
  coast, derivative filtering, anti-windup, marker debounce, lost-line timeout, and
  stall timeout. No separately reimplemented controller model is accepted as a
  substitute. The Arduino compile remains a second compatibility check.
- Generated representative sketches compile without the current
  `-Wmaybe-uninitialized` warnings.
- Browser tests verify Compile success closes PROGRAM, Compile failure keeps it
  open, Upload success shows the disconnect message, failure keeps details visible,
  and reloading uses versioned local assets.
- Run the existing test suite and production build.

### Hardware

Use a charged Leanbot on the intended black-line/white-background surface and record
at least five repetitions for each case:

- Move forward and backward 30 cm at Speed 50.
- Turn left and right 90 degrees at Speed 50.
- Follow straight and curved line sections at Speed 50.
- Stop at Left, Right, and T markers.
- Repeat at low and high battery levels after line-sensor calibration.

Record elapsed time, final distance error, final angle error, line-loss events, and
marker overshoot. Provisional pass thresholds are: 30 cm absolute distance error at
most 15 mm median and 25 mm worst run; 90-degree absolute turn error at most 5
degrees median and 8 degrees worst run after fine correction; no line loss in five
complete runs; and marker overshoot at most 30 mm. Speed-50 30 cm median elapsed
time must be at least 15% lower than the current controller on the same robot,
battery, and surface. Tune only centralized constants from those measurements; do
not change block contracts during calibration.

## Acceptance Criteria

- Compile success restores the full editor automatically; Compile failure remains
  diagnosable in PROGRAM.
- Upload success explicitly tells the user the USB cable may be disconnected;
  upload failures remain diagnosable.
- After the current HTML is fetched, a normal reload requests every locally changed
  asset with version token `20260930-2` and shows no blank/malformed layout.
- The My Blocks category and all its blocks are blue `#3373CC`.
- Speed remains a linear `0..100` user scale and generated wheel commands never
  exceed the Leanbot limit.
- Speed 50 reaches 1000 steps/s within 200 ms when braking is not active.
- The simulated turn controller settles a 90-degree command within 2 degrees after
  at most two fine passes under the test coast model; Gate C meets the stated
  five-run physical turn thresholds before being called calibrated.
- Generated sketches compile without the uninitialized-context warnings.
- Software tests pass, and hardware results are recorded before final PID constants
  are described as calibrated.
