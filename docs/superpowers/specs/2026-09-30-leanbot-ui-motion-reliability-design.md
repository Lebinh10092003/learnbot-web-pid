# Leanbot UI And Motion Reliability Design

## Outcome

Improve the imported LeanbotSerial IDE without changing its overall structure or
the public shape of the eight My Blocks. A successful Compile returns the user to
the full editor, Upload gives an explicit success or failure message, stale static
assets no longer cause blank or malformed layouts, and generated My Blocks code
moves more responsively while keeping the documented Leanbot speed limit and
improving motion accuracy.

The **My Blocks** toolbox category and every block in that category use the same
blue `#3373CC` already used by the Leanbot Motion category. Existing serialized
Blockly projects remain compatible because block type names and field/input names
do not change.

## Scope

This change covers two connected areas:

1. The existing Compile/Upload feedback and editor-panel lifecycle in the imported
   IDE.
2. The C++ runtime generated by the eight existing My Blocks.

It does not replace the Leanbot library, bypass its motor scheduler, or drive the
stepper pins directly. `LbMotion.runLR()` remains the only wheel-command boundary.
Its documented range is `-2000..2000` steps per second, so the public Speed scale
continues to map linearly from `0..100` to `0..2000`. Move alone accepts negative
Speed for reverse motion.

## UI Behaviour

### Compile

- Clicking Compile opens the PROGRAM panel and shows progress as it does today.
- On a successful compile, a success toast is shown and the PROGRAM panel closes
  automatically after a short delay, restoring the full editor height.
- If the compiler returns warnings, compilation is still successful. The toast
  reports that warnings exist before the panel closes; the log remains available
  by reopening SERIAL/PROGRAM.
- On a compile error, the PROGRAM panel remains open, the progress state is marked
  as failed, and the existing compiler log remains visible.
- Compile controls and the file tree are always re-enabled in a `finally` path, so
  a rejected request cannot leave the IDE looking frozen or blank.

### Upload

- A successful upload displays: `Upload Successful — You Can Disconnect The USB
  Cable And Run The Robot.`
- After success the existing transition to the serial monitor remains intact.
- Cancellation is reported as cancellation, not as a generic error.
- Connection, compile, transfer, write, and verify failures keep the PROGRAM panel
  open and show a concise error toast while retaining the detailed log.
- Controls are restored in a `finally` path for every outcome.

### Static Assets And Layout

- Locally modified CSS and JavaScript entry points receive one shared version query
  so a normal reload cannot combine new HTML with stale layout or behaviour files.
- The Blockly iframe entry point receives the same version at its parent boundary.
- The current flex/grid layout stays unchanged. The fix removes the cache mismatch
  that can create blank or malformed regions rather than redesigning the IDE.

## My Blocks Appearance

- Change `myblocks_category.colour` from pink to `#3373CC` in the Blockly theme.
- The toolbox category and all eight blocks already reference
  `myblocks_category`, so one theme-token change updates both consistently.
- Do not add per-block colours or duplicate CSS overrides.

## Generated Motion Runtime

### Shared Rules

- Speed mapping remains predictable and linear: `abs(speedPercent) * 20`, clamped
  to `0..2000` steps per second.
- Every context is value-initialized (`ctx = {}`) before use. This removes the AVR
  uninitialized-field warnings and makes initialization safe if control flow later
  changes.
- Invalid numbers, zero speed, out-of-range target values, a lost line, or a stall
  always stop through `LbMotion.stopAndWait()` and return.
- The core controller remains Arduino-independent: state enters through fixed-width
  structs and wheel commands leave through `LbmbCommand`. Arduino wrapper code only
  reads sensors/odometry, calls the core step, and applies `LbMotion.runLR()`.

### Move With Speed And Distance

- Replace the long distance-proportional acceleration zone with a quicker bounded
  slew-rate ramp. At Speed 50, the command reaches 1000 steps/s substantially
  faster than the current roughly 0.67-second ramp.
- Keep distance-aware deceleration near the target so responsiveness does not trade
  away stopping accuracy.
- Use the starting body rotation as a heading reference. A small bounded PD
  correction adjusts left/right speeds when odometry reports heading drift.
- Reverse travel preserves the user's negative Speed direction while applying the
  heading correction with the correct sign.

### Turn Left/Right

- Continue measuring body rotation with `LbMotion.getRotationDeg()`; wheel rotation
  is not exposed to the block contract.
- Use the same quicker acceleration policy and an angle-aware braking zone.
- Bound both wheel commands to the Leanbot range and approach the target at a low
  nonzero speed before stopping, reducing overshoot without stalling the motors.

### FLL Controllers

- Keep `LbIRLine.read()` as the authoritative source for line-presence and
  Left/Right/T marker detection.
- Read the four line sensors through `LbIRArray.read()` for a continuous weighted
  line-position estimate. Remove the common background level before calculating
  the centroid so the controller is less sensitive to ambient brightness.
- When analog contrast is insufficient, fall back to the existing discrete
  `LbIRLine` error table rather than issuing an arbitrary correction.
- Use a bounded PID/PD correction with filtered derivative and anti-windup. The
  correction limit is speed-aware: ordinary deviations preserve forward momentum,
  while extreme edge states may slow the inner wheel further to recover a sharp
  curve.
- Acceleration reaches the requested base speed faster. Distance and time variants
  retain target-aware deceleration. Marker variants retain consecutive-sample
  debouncing before stopping.
- Calibration remains the responsibility of the existing Leanbot calibration API;
  this change does not insert an interactive calibration sequence into every My
  Block call.

## Boundaries And Data Flow

```text
Blockly values
  -> generator validation and C++ helper emission
  -> Arduino wrapper reads time, odometry, digital line state, analog sensors
  -> pure motion/FLL core calculates bounded left/right commands
  -> LbMotion.runLR()
  -> stop condition calls LbMotion.stopAndWait()
```

The UI flow remains separate:

```text
Compile/Upload click
  -> lock controls and open PROGRAM
  -> compiler/uploader callbacks update progress and log
  -> success toast + requested panel transition
     OR failure toast + keep PROGRAM open
  -> finally restore controls
```

## Error Handling And Safety

- Never generate wheel commands outside `-2000..2000`.
- Never attempt a direct-stepper workaround to exceed the Leanbot API limit.
- Preserve stall and lost-line timeouts so a blocked or derailed robot stops.
- Preserve marker and overall-operation timeouts.
- Clamp heading and line corrections before combining them with base speed.
- Do not claim physical PID completion from software tests alone. Final constants
  require repeatable runs on the actual robot and track.

## Verification

### Automated

- Static/generator tests confirm all eight blocks retain their public types and emit
  the expected helper calls.
- Theme tests confirm `myblocks_category` is blue and all My Blocks reference it.
- Pure C++ controller tests cover linear speed mapping, quicker ramp-up, command
  bounds, forward/reverse heading correction, turn braking, analog line-centroid
  calculation, discrete fallback, anti-windup, marker debounce, lost-line timeout,
  and stall timeout.
- Generated representative sketches compile without the current
  `-Wmaybe-uninitialized` warnings.
- Browser tests verify Compile success closes PROGRAM, Compile failure keeps it
  open, Upload success shows the disconnect message, failure keeps details visible,
  and reloading uses versioned local assets.
- Run the existing test suite and production build.

### Hardware

Use a charged Leanbot on the intended black-line/white-background surface and record
at least five repetitions for each case:

- Move forward and backward 30 cm at Speed 50.
- Turn left and right 90 degrees at Speed 50.
- Follow straight and curved line sections at Speed 50.
- Stop at Left, Right, and T markers.
- Repeat at low and high battery levels after line-sensor calibration.

Record elapsed time, final distance error, final angle error, line-loss events, and
marker overshoot. Tune only the centralized constants from those measurements; do
not change block contracts during calibration.

## Acceptance Criteria

- Compile success restores the full editor automatically; Compile failure remains
  diagnosable in PROGRAM.
- Upload success explicitly tells the user the USB cable may be disconnected;
  upload failures remain diagnosable.
- A normal reload does not show a stale blank/malformed layout after deployment.
- The My Blocks category and all its blocks are blue `#3373CC`.
- Speed remains a linear `0..100` user scale and generated wheel commands never
  exceed the Leanbot limit.
- Speed 50 reaches its 1000-step/s target faster than the current controller.
- Generated sketches compile without the uninitialized-context warnings.
- Software tests pass, and hardware results are recorded before final PID constants
  are described as calibrated.
